Авторизация пользователя производится посредством JWT токена, передаваемого в Cookies.

## 1) Авторизация (проверка сессии) — Back-end / Front-end

### 1.1 Общее

**Назначение:** аутентифицировать запросы пользователя на основе JWT, полученного из Cookies.

**Пользователи/роли:** любой пользователь, выполняющий запросы к защищённым ресурсам.

**Зависимости/связанные настройки:**

- Секрет/ключ подписи JWT (и алгоритм подписи).
- Параметры cookies (domain, path, Secure, HttpOnly, SameSite).
- Используются два JWT: **access token** и **refresh token**.
- **TTL:** access — **15 минут**, refresh — **30 дней**.
- **Ротация refresh:** включена. При каждом успешном refresh выдавать **новую пару** (access+refresh).
- **Хранение refresh на сервере:** **запрещено** (не хранить allowlist/denylist; не сохранять refresh JWT, `jti`, session-идентификаторы, связанные с refresh).
    - Следствие: серверная инвалидация refresh (logout/компрометация/повторное использование) недоступна; действуем по TTL и очистке cookies на клиенте.

### 1.2 Сценарии (user stories)

1. **Доступ к защищённому ресурсу (access валиден):** пользователь отправляет запрос с cookies, сервер валидирует access JWT и разрешает доступ.
2. **Access истёк, refresh валиден:** пользователь выполняет refresh, получает новый access (и, при ротации, новый refresh), затем повторяет запрос.
3. **Refresh истёк/невалиден:** пользователь получает 401 и должен заново войти.
4. **Выход (опционально):** refresh токен инвалидируется, cookies очищаются.

### 1.3 Контракт / API (если применимо)

#### 1.3.1 Проверка авторизации на защищённых endpoint’ах

**Входные данные:**

- Cookie `access_token` со значением access JWT.

**Проверки/валидация:**

- Cookie присутствует.
- JWT подпись валидна (по текущему ключу/набору ключей).
- `exp` не истёк.
- `nbf`/`iat` (если используются) валидны.
- `iss`/`aud` (если используются) соответствуют настройкам.
- `sub` (идентификатор пользователя) присутствует.

**Логика/шаги:**

1. Извлечь JWT из Cookies.
2. Провалидировать JWT (подпись + claims).
3. Получить пользователя по `sub`.
4. Проверить статус пользователя (активен/заблокирован) — если применимо.
5. Пробросить `userId`/контекст пользователя в обработчик запроса.

**Ответы:**

- **Успех:** запрос выполняется, возвращается ответ endpoint’а.
- **Ошибка:** см. раздел 1.4.

#### 1.3.2 Установка cookies при входе и при refresh (если описывается в рамках этого ТЗ)

**Общее правило:**

- При входе выставлять `access_token` и `refresh_token`.
- При refresh выставлять новый `access_token` (и, при ротации, новый `refresh_token`).

**Входные данные (refresh):**

- Cookie `refresh_token` со значением refresh JWT.

**Проверки/валидация (refresh):**

- Cookie присутствует.
- JWT подпись валидна.
- `exp` не истёк.
- Дополнительных серверных проверок по состоянию refresh нет (так как хранение запрещено).

**Ответы (refresh):**

- **Успех:** выставить новый `access_token` (и опционально новый `refresh_token`).
- **Ошибка:** 401.

**Рекомендуемые требования к cookie:**

- `HttpOnly: true` (чтобы JS не мог читать токен).
- `Secure: true` (только HTTPS).
- `SameSite: Lax/Strict` (выбрать по требованиям; для кросс-доменных сценариев может потребоваться `None` + `Secure`).
- TTL cookie синхронизирован с `exp` токена.

### 1.4 Ошибки и ограничения

- Cookie с JWT отсутствует.
- JWT невалиден (подпись/формат).
- JWT истёк.
- Пользователь не найден / заблокирован.
- Refresh token отсутствует/невалиден/истёк.
- Logout не может инвалидировать уже выданный refresh на сервере; logout = очистка cookies (и, при необходимости, клиентский редирект на login).

### 1.5 Аудит/логи (если требуется)

- Логировать: неуспешные проверки JWT (причина без утечки секретных данных), попытки доступа к защищённым ресурсам.
- Не логировать: полный JWT, секреты, чувствительные персональные данные.

### 1.6 Нефункциональные требования

- Безопасность: защита от XSS/CSRF через корректные настройки cookies; минимизация утечек в логах.
