## 1) Просмотр списка всех пользователей — Back-end

### 1.1 Общее

**Назначение:** предоставить администратору список пользователей с возможностью поиска/фильтрации.

**Роли:**

- **Admin:** доступ разрешён.
- **Другие роли:** запретить (если не определены отдельные права).

**Контекст/предпосылки:**

- Авторизация через access JWT (cookie).
- Авторизация через RBAC.

**Зависимости/связанные настройки:**

- Индексы/поиск по пользователям (если нужен быстрый поиск).
- Хранение фото пользователей (URL/файл).

### 1.2 Сценарии

1. **Admin получает список:** клиент запрашивает список пользователей → получает страницу результатов.
2. **Admin ищет/фильтрует:** клиент задаёт параметры поиска/фильтров → получает отфильтрованный список.
3. **Без права:** запрос списка без прав администратора → 403.

### 1.3 Контракт

#### 1.3.1 Получение списка пользователей

**Операция:** `GET /admin/users` (или `GET /users` с правом admin — выбрать один подход)

**Query параметры:**

- `cursor: string | null` — курсор пагинации (опционально)
- `limit: number` — размер страницы (например, 20–100)
- `q: string` — поисковая строка (опционально: email/имя/id)
- `status: "active" | "blocked" | "deleted"` — фильтр (опционально)
- `sort: "created_at" | "last_login" | "email"` — сортировка (опционально)
- `order: "asc" | "desc"` — направление (опционально)

**Выходные данные:**

- `items: UserListItem[]`
- `nextCursor: string | null`

`UserListItem`:

- `id: string`
- `email: string` (или маскировать часть — требует решения)
- `photo: string | null` — URL фото профиля (если загружено)
- `createdAt: datetime`
- `status: string`
- (опционально) `lastLoginAt: datetime | null`

**Проверки/валидация:**

- Авторизация (JWT валиден).
- Проверить право администратора (например `users.list.admin`).
- `limit` в допустимых границах.
- Валидировать `cursor`, `sort`, `order`, `status`.

**Логика/шаги:**

1. Авторизовать запрос.
2. Сформировать запрос к хранилищу пользователей с учётом фильтров/поиска.
3. Вернуть paginated-результат.

**Ответы:**

- **200 OK:** список пользователей.
- **401 Unauthorized:** нет/невалидный JWT.
- **403 Forbidden:** нет прав.

### 1.4 Ошибки и ограничения

- Rate limit на endpoint списка.
- Ограничить возможные поля поиска, чтобы избежать тяжёлых запросов.
- Запретить выдачу чувствительных полей (пароли/хэши, токены, 2FA-секреты, внутренние флаги).

### 1.5 Аудит/логи

- Логировать: `actorUserId`, параметры запроса (без PII, где возможно), результат (200/403), количество возвращённых элементов.

### 1.6 Нефункциональные требования

- Безопасность: строгая RBAC-проверка, минимизация PII.
- Производительность: обязательная пагинация, индексы для фильтров/поиска.
- Надёжность: стабильная курсорная пагинация (предпочтительно) и идемпотентность ответа при одинаковых параметрах.
