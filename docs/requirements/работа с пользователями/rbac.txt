### Суть

Конфигурация RBAC (роли, разрешения, правила) хранится в базе данных и может изменяться без перезапуска приложения.

### Конфигурация

Набор правил доступа (роли → разрешения → действия) хранится в БД и загружается при старте приложения.

### Проверка доступа

1. Пользователь запрашивает ресурс с указанием требуемого разрешения (`ресурс@действие`)
2. Система проверяет, есть ли у роли пользователя это разрешение в загруженной конфигурации
3. Результат: доступ разрешён или запрещён (403)

### Динамическое обновление

- Изменение правил в БД → сброс кеша → перезагрузка конфигурации
- Изменения применяются без перезапуска приложения

### Сущности в БД

- **Роли** — список ролей
- **Разрешения** — ресурсы и допустимые действия (`create`, `update`, `delete`)
- **Назначения** — связь "роль → разрешение → действие" (если действие не указано — доступны все)

### Преимущества

- Изменение прав без деплоя
- Гибкое назначение действий для каждой роли
- Централизованное управление доступом

## 1) RBAC (Role-Based Access Control)

### 1.1 Общее

**Назначение:** централизованное управление доступом на основе ролей и разрешений. Конфигурация хранится в БД и применяется без перезапуска приложения.

**Пользователи/роли:**

- **Admin:** управляет ролями, разрешениями и назначениями.
- **Пользователь:** субъект проверки доступа (носитель одной или нескольких ролей).

**Контекст/предпосылки:**

- Авторизация запросов выполняется после аутентификации (JWT).
- RBAC не привязан к конкретному фреймворку.

**Зависимости/связанные настройки:**

- БД (хранение ролей, разрешений, назначений).
- Кеш (опционально, для быстрой проверки прав).
- Механизм инвалидации кеша.

### 1.2 Сценарии

1. **Проверка доступа:** пользователь запрашивает действие (например, просмотр списка пользователей) → система проверяет право → доступ разрешён или 403.
2. **Динамическое обновление:** администратор изменяет правила в БД → кеш сбрасывается → конфигурация перезагружается → новые правила применяются без перезапуска.
3. **Загрузка конфигурации при старте:** приложение загружает роли, разрешения и назначения из БД → конфигурация готова к проверкам.

### 1.3 Контракт

#### 1.3.1 Проверка доступа

**Входные данные (внутренний вызов модуля RBAC):**

- `userId: string` — идентификатор пользователя (из JWT).
- `roles: string[]` — роли пользователя (из БД или кеша).
- `permission: string` — идентификатор разрешения (например `permission1`).
- `action: string` — действие в рамках разрешения (`create`, `update`, `delete`и т.д.).

**Проверки/валидация:**

- Пользователь аутентифицирован.
- Роли пользователя существуют в конфигурации.
- Разрешение существует в конфигурации.
- Действие допустимо для разрешения.

**Логика/шаги:**

1. Получить роли пользователя.
2. Для каждой роли найти назначения (grants) в загруженной конфигурации.
3. Проверить наличие разрешения и действия.
4. Если назначение содержит разрешение без указания действия — доступны все действия разрешения.
5. Если назначение содержит разрешение с действием — доступно только указанное действие.
6. Если найдено совпадение — доступ разрешён.
7. Если совпадений нет — вернуть 403.

**Ответы:**

- **Доступ разрешён:** продолжить выполнение запроса.
- **403 Forbidden:** доступ запрещён.

#### 1.3.2 Управление ролями

**Операции:**

- `GET /admin/rbac/roles` — список ролей.
- `POST /admin/rbac/roles` — создать роль.
- `PUT /admin/rbac/roles/{roleId}` — обновить роль.
- `DELETE /admin/rbac/roles/{roleId}` — удалить роль.

**Входные данные:**

- `role: { id: string, name: string, description?: string }`

**Проверки:**

- Только Admin.
- Название роли уникально.
- Нельзя удалить роль, если есть назначения (или каскадно удалить — требует решения).

**Ответы:** 200 / 201 / 400 / 403 / 404 / 409.

#### 1.3.3 Управление разрешениями

**Операции:**

- `GET /admin/rbac/permissions` — список разрешений.
- `POST /admin/rbac/permissions` — создать разрешение.
- `PUT /admin/rbac/permissions/{permissionId}` — обновить разрешение.
- `DELETE /admin/rbac/permissions/{permissionId}` — удалить разрешение.

**Входные данные:**

- `permission: { id: string, name: string, actions: string[] }`

**Пояснение:**

- `name` — идентификатор разрешения (например `permission1`, `permission2`).
- `actions` — список допустимых действий для этого разрешения (например `['create', 'update', 'delete']`).

**Проверки:**

- Только Admin.
- Название разрешения уникально.
- Нельзя удалить разрешение, если есть назначения.

**Ответы:** 200 / 201 / 400 / 403 / 404 / 409.

#### 1.3.4 Управление назначениями (grants)

**Операции:**

- `GET /admin/rbac/grants` — список назначений.
- `POST /admin/rbac/grants` — создать назначение.
- `PUT /admin/rbac/grants/{grantId}` — обновить назначение.
- `DELETE /admin/rbac/grants/{grantId}` — удалить назначение.

**Входные данные:**

- `grant: { id: string, roleId: string, permissionId: string, actions?: string[] }`

**Пояснение:**

- Если `actions` не указано или пусто — доступны все действия разрешения.
- Если `actions` указано — доступны только перечисленные действия.

**Проверки:**

- Только Admin.
- Роль и разрешение существуют.
- Дубликат назначения (та же роль + разрешение) запрещён.

**Ответы:** 200 / 201 / 400 / 403 / 404 / 409.

### 1.4 Ошибки и ограничения

- Роль не найдена.
- Разрешение не найдено.
- Назначение не найдено.
- Дубликат роли/разрешения/назначения.
- Попытка удалить сущность с активными назначениями.
- Невалидный формат действия или разрешения.

### 1.5 Аудит/логи

- Логировать: `actorUserId`, операция (create/update/delete), сущность (role/permission/grant), результат (200/403/409).
