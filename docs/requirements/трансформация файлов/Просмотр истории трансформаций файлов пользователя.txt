## 1) Просмотр истории трансформаций

### 1.1 Общее

**Назначение:** предоставить пользователю и администратору доступ к истории выполненных трансформаций (файлы и изображения).

**Пользователи/роли:**

- **Self:** просмотр только своих трансформаций.
- **Admin:** просмотр трансформаций любого пользователя.

**Контекст/предпосылки:**

- Авторизация через access JWT (cookie).
- Все трансформации (файлы и изображения) логируются в единое хранилище истории.

**Зависимости/связанные настройки:**

- Хранилище истории трансформаций (БД).
- Пагинация (курсорная или offset — выбрать один подход; рекомендуется cursor).
- Поля записи истории формируются из данных аудита (см. 1.5).

### 1.2 Сценарии

1. **Пользователь смотрит свою историю:** Self запрашивает список своих трансформаций → получает страницу результатов.
2. **Администратор смотрит историю конкретного пользователя:** Admin запрашивает историю по `userId` → получает страницу результатов.
3. **Администратор фильтрует:** Admin задаёт параметры фильтрации (тип, формат, статус, дата) → получает отфильтрованный список.
4. **Без права:** попытка доступа к чужой истории без прав администратора → 403.

### 1.3 Контракт

#### 1.3.1 Получение собственной истории трансформаций

**Операция:** `GET /api/transformations/history`

**Query параметры:**

- `cursor: string | null` — курсор пагинации (опционально)
- `limit: number` — размер страницы (по умолчанию 20, максимум 100)
- `type: "file" | "image"` — тип трансформации (опционально)
- `sourceFormat: string` — исходный формат (опционально: csv, json, xml, yaml, png, jpeg, svg)
- `targetFormat: string` — целевой формат (опционально)
- `status: "success" | "error"` — статус (опционально)
- `createdAtFrom: datetime` — начало периода (опционально)
- `createdAtTo: datetime` — конец периода (опционально)

**Выходные данные:**

- `items: TransformationHistoryItem[]`
- `nextCursor: string | null`

`TransformationHistoryItem`:

- `id: string`
- `type: "file" | "image"`
- `sourceFormat: string`
- `targetFormat: string`
- `status: "success" | "error"`
- `fileSize: number` — размер исходного файла в байтах
- `durationMs: number` — длительность трансформации
- `errorCode?: string` — код ошибки, если `status = "error"`
- `createdAt: datetime`

**Проверки/валидация:**

- Авторизация (JWT валиден).
- Пользователь существует и активен.
- `limit` в допустимых границах.
- `type`, `sourceFormat`, `targetFormat`, `status` — допустимые значения.
- `cursor` валиден.

**Логика/шаги:**

1. Авторизовать запрос.
2. Определить `userId` из JWT.
3. Сформировать запрос к хранилищу истории с фильтром по `userId = self`.
4. Вернуть paginated-результат.

**Ответы:**

- **200 OK:** список записей истории.
- **401 Unauthorized:** неаутентифицированный запрос.

#### 1.3.2 Получение истории трансформаций конкретного пользователя (Admin)

**Операция:** `GET /admin/users/{userId}/transformations/history`

**Query параметры:** аналогично 1.3.1.

**Выходные данные:** аналогично 1.3.1.

**Проверки/валидация:**

- Авторизация (JWT валиден).
- Проверить право администратора (например `transformations.history.admin`).
- Пользователь с `userId` существует.
- Остальные параметры аналогично 1.3.1.

**Логика/шаги:**

1. Авторизовать запрос.
2. Проверить право администратора.
3. Сформировать запрос к хранилищу истории с фильтром по `userId = {userId}`.
4. Вернуть paginated-результат.

**Ответы:**

- **200 OK:** список записей.
- **401 Unauthorized:** неаутентифицированный запрос.
- **403 Forbidden:** нет прав администратора.
- **404 Not Found:** пользователь не найден.

### 1.4 Ошибки и ограничения

- Попытка доступа к чужой истории без прав администратора.
- Невалидные параметры фильтрации/пагинации.
- Rate limit на endpoint истории (особенно для администратора).
- Не раскрывать чувствительные данные других пользователей (email и т.п.) в записях истории.

### 1.5 Аудит/логи

- Логировать: `actorUserId`, `targetUserId` (для админ-доступа), параметры запроса (без PII, где возможно), результат (200/403/404), количество возвращённых записей.
- Не логировать содержимое файлов/изображений.

### 1.6 Нефункциональные требования

- **Безопасность:** строгая проверка доступа: Self — только свои записи; Admin — только по праву.
- **Производительность:** обязательная пагинация; индексы в хранилище истории по `userId`, `createdAt`, `type`, `status`.
- **Надёжность:** идемпотентность ответа при одинаковых параметрах.
- **Хранение:** срок хранения истории определяется администратором (например, 90 дней — на собственное усмотрение).
