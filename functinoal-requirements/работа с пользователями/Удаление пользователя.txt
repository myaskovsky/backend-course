## 1) Удаление пользователя — Back-end

### 1.1 Общее

**Назначение:** удалить (или анонимизировать) персональные данные пользователя по запросу и правилам доступа.

**Роли:**

- **Self:** может запросить удаление собственных данных.
- **Admin:** может удалить данные любого пользователя.

**Контекст/предпосылки:**

- Пользователь аутентифицируется через access JWT (cookie).
- Авторизация через RBAC.

### 1.2 Сценарии

1. **Self запрашивает удаление:** клиент инициирует удаление своего аккаунта → система удаляет/обезличивает данные → пользователь больше не может войти.
2. **Admin удаляет пользователя:** администратор инициирует удаление целевого пользователя → система удаляет/обезличивает данные.
3. **Без права:** попытка удалить чужого пользователя без прав → 403.

### 1.3 Контракт

#### 1.3.1 Запрос удаления пользователя

**Операция:** `DELETE /users/{userId}` (или `POST /users/{userId}/delete` — выбрать один подход)

**Входные данные:**

- `userId: string` (path)
- (опционально) `reason: string` — причина (для аудита/поддержки)

**Проверки/валидация:**

- Авторизация (JWT валиден).
- Пользователь существует.
- Доступ:
    - Self: `userId` совпадает с текущим пользователем.
    - Admin: право `users.delete` (или эквивалент).
- **Нужно:** перед self-delete обязательно подтверждение по email (OTP-код или magic link), аналогично другим флоу приложения. Удаление без подтверждения — запретить.

**Логика/шаги:**

1. Проверить права (Self/Admin).
2. Выполнить деактивацию доступа:
    - отозвать активные сессии/refresh-токены;
    - запретить дальнейшую аутентификацию.
3. Запустить процесс удаления/обезличивания:
    - удалить/обезличить профильные поля (PII);
    - удалить файлы (фото/вложения), если они относятся к пользователю;
    - обработать связанные сущности.
4. Завершить операцию синхронно **или** поставить в очередь (если долго) — требует выбора.

**Ответы:**

- **200 OK / 204 No Content:** удаление принято/выполнено.
- **202 Accepted:** удаление поставлено в очередь (асинхронно) + `jobId`.
- **Ошибки:** см. раздел 1.4

#### 1.3.2 Статус удаления (если асинхронно)

**Операция:** `GET /users/{userId}/deletion-status` (или `GET /jobs/{jobId}`)

**Выход:** `status: "pending" | "in_progress" | "done" | "failed"`.

### 1.4 Ошибки и ограничения

- **401 Unauthorized:** нет/невалидный JWT.
- **403 Forbidden:** нет прав.
- **404 Not Found:** пользователь не найден.
- **409 Conflict:** удаление уже запущено / пользователь в состоянии "deleting".
- **429 Too Many Requests:** rate limit на операции удаления.

### 1.5 Аудит/логи

- Логировать: `actorUserId`, `targetUserId`, тип операции (self/admin), результат (успех/ошибка), `jobId` (если есть).
- Не логировать удаляемые PII-значения.

### 1.6 Нефункциональные требования

- Безопасность: защита от IDOR, строгие права `users.delete`.
- Надёжность: идемпотентность удаления (повторный вызов не ломает систему).
