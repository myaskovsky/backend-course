## 1) Просмотр данных пользователя

### 1.1 Общее

**Назначение:** показать профиль пользователя по правилам доступа.

**Роли:** Self (свой профиль), Support/Admin (чужой профиль — только при наличии права).

**Зависимости:** access JWT (cookie), RBAC, хранение фото (URL/файл).

### 1.2 Сценарии

1. **Self:** клиент запрашивает `GET /users/{userId}` для своего `userId` → получает свой профиль.
2. **Роль с правом:** клиент запрашивает `GET /users/{userId}` для чужого `userId` → получает только разрешённые поля.
3. **Без права:** попытка просмотра чужого профиля → 403.

### 1.3 Контракт

#### 1.3.1 Получение профиля пользователя

**Операция:** `GET /users/{userId}`

**Вход:** `userId: string`, access JWT (cookie).

**Выход (минимум):** `id`, `email`, `photo`, `fields` (только разрешённые поля).

**Проверки:**

- Авторизация (JWT валиден).
- Пользователь существует.
- Доступ: Self **или** право `users.read`.

**Правила формирования ответа:**

- Фильтровать поля профиля на стороне API по роли/правам (default-deny).
- Список разрешённых полей для Self/ролей — задаётся политикой/конфигурацией (требует фиксации, если ещё не определён).

**Ответы:** 200 / 401 / 403 / 404.

### 1.4 Ошибки и ограничения

- Rate limit на чтение профилей (особенно для просмотра чужих).
- Default-deny по полям: выдавать только разрешённые.

### 1.5 Аудит (опционально)

- Логировать: `viewerUserId`, `targetUserId`, результат (200/403/404).

### 1.6 Нефункциональные требования

- Защита от IDOR (Self только для себя).
