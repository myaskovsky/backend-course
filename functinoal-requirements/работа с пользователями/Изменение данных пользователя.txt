## 1) Изменение данных пользователя — Back-end

### 1.1 Общее

**Назначение:** изменить данные профиля пользователя по правилам доступа.

**Роли:**

- **Self:** может менять свои данные, кроме `email` (только через подтверждение).
- **Admin:** может менять любые поля пользователя (включая `email`) напрямую.

**Контекст/предпосылки:**

- Пользователь аутентифицируется через access JWT (cookie).
- Авторизация через RBAC (права/роли).

**Зависимости/связанные настройки:**

- Email-сервис для отправки кода/ссылки подтверждения.
- Хранилище/URL для фото (если меняется).

### 1.2 Сценарии

1. **Self меняет профиль (без email):** клиент отправляет изменения разрешённых полей → профиль обновляется.
2. **Self меняет email через подтверждение:** клиент инициирует смену email → получает требование подтверждения → подтверждает кодом/ссылкой → email меняется.
3. **Admin меняет профиль/почту:** клиент с правами администратора меняет любые поля пользователя напрямую.
4. **Без права:** попытка изменить чужого пользователя/запрещённые поля → 403.

### 1.3 Контракт

#### 1.3.1 Обновление данных пользователя (кроме email для Self)

**Операция:** `PATCH /users/{userId}`

**Входные данные:**

- `userId: string` (path)
- `patch: object` — поля, которые нужно изменить (разрешённый набор должен быть зафиксирован)

**Проверки/валидация:**

- Авторизация (JWT валиден).
- Пользователь существует.
- Доступ:
    - Self: `userId` должен совпадать с текущим пользователем.
    - Admin: требуется право `users.update` (или эквивалент).
- **Запретить:** Self менять `email` через этот endpoint.
- Валидировать значения полей по формату/ограничениям (для каждого поля).

**Логика/шаги:**

1. Проверить права и принадлежность (Self vs Admin).
2. Проверить, что в `patch` нет запрещённых полей для данной роли.
3. Применить изменения и сохранить.

**Ответы:**

- **200 OK:** обновлённый профиль (только разрешённые поля) или подтверждение успеха.
- **Ошибки:** см. раздел 1.4

#### 1.3.2 Инициация смены email (Self)

**Операция:** `POST /users/{userId}/email-change`

**Входные данные:**

- `userId: string` (path)
- `newEmail: string`
- `method: "otp" | "magic_link"` (или выбирается сервером)

**Проверки/валидация:**

- Авторизация (JWT валиден).
- Доступ: только Self (userId = текущий пользователь).
- `newEmail` валиден по формату.
- `newEmail` не занят другим пользователем (или политика должна быть определена).

**Логика/шаги:**

1. Создать запрос на смену email (pending) с TTL.
2. Отправить подтверждение на `newEmail`:
    - OTP код, или
    - ссылка (magic link) с токеном.

**Ответы:**

- **200 OK:** `requiresConfirmation: true` и `challengeId` (если нужно).
- **Ошибки:** см. раздел 1.4

#### 1.3.3 Подтверждение смены email (Self)

**Операция:** `POST /users/{userId}/email-change/confirm`

**Вариант A (OTP):** `challengeId: string`, `code: string`  

**Вариант B (magic link):** `token: string`

**Проверки/валидация:**

- Авторизация (JWT валиден) **или** (опционально) токен magic link самодостаточен — требует уточнения.
- Доступ: только Self.
- Проверить TTL, лимиты попыток, соответствие кода/токена.

**Логика/шаги:**

1. Верифицировать код/токен.
2. Обновить `email` пользователя.
3. Инвалидировать challenge/токен.

**Ответы:**

- **200 OK:** email изменён.
- **Ошибки:** см. раздел 1.4

#### 1.3.4 Прямое изменение email (Admin)

**Операция:** `PATCH /users/{userId}` (через общий endpoint) **или** отдельный `PATCH /users/{userId}/email` — выбрать один.

**Правило:** Admin может менять `email` без подтверждения.

### 1.4 Ошибки и ограничения

- **400 Bad Request:** неверные форматы полей.
- **401 Unauthorized:** нет/невалидный JWT.
- **403 Forbidden:** нет прав / попытка Self поменять `email` напрямую.
- **404 Not Found:** пользователь не найден.
- **409 Conflict:** `newEmail` занят (если применяется).
- **429 Too Many Requests:** rate limit на изменение профиля / отправку подтверждений.
- Для подтверждения email:
    - TTL (например 10 минут) — требует фиксации.
    - Лимит попыток (например 5) — требует фиксации.
    - Повторная отправка (например 60 секунд) — требует фиксации.

### 1.5 Аудит/логи

- Логировать:
    - кто менял (`actorUserId`), кого (`targetUserId`), какие поля (только имена полей, без значений), результат.
    - события email-change: инициировано/отправлено/подтверждено/ошибка/истёк TTL.

### 1.6 Нефункциональные требования

- Безопасность:
    - Default-deny по изменяемым полям.
    - Защита от IDOR (Self только для себя).
- Производительность: обновление профиля — 1 транзакция/минимум запросов.
- Надёжность: отправка email — через очередь/ретраи (если есть).
