## 1) Трансформация файлов

### 1.1 Общее

**Назначение:** конвертация файлов между форматами CSV, JSON, XML, YAML.

**Пользователи/роли:**

- Только аутентифицированный пользователь.

**Контекст/предпосылки:**

- Авторизация через access JWT (cookie).
- Доступ к endpoint’у только после аутентификации.

**Зависимости/связанные настройки:**

- Библиотеки парсинга/сериализации для CSV, JSON, XML, YAML, или собственные реализации парсинга/сериализации.
- Лимиты размера файлов: устанавливаются администратором в конфигурации приложения отдельно для каждого входного формата (CSV, JSON, XML, YAML).
- Потоковая обработка файлов.

### 1.2 Сценарии

1. **CSV → JSON:** пользователь загружает CSV, получает JSON.
2. **JSON → CSV:** пользователь загружает JSON, получает CSV.
3. **XML → JSON:** пользователь загружает XML, получает JSON.
4. **JSON → XML:** пользователь загружает JSON, получает XML.
5. **YAML → JSON:** пользователь загружает YAML, получает JSON.
6. **JSON → YAML:** пользователь загружает JSON, получает YAML.
7. **CSV → XML:** пользователь загружает CSV, получает XML.
8. **XML → CSV:** пользователь загружает XML, получает CSV.
9. **CSV → YAML:** пользователь загружает CSV, получает YAML.
10. **YAML → CSV:** пользователь загружает YAML, получает CSV.
11. **XML → YAML:** пользователь загружает XML, получает YAML.
12. **YAML → XML:** пользователь загружает YAML, получает XML.
13. **Список поддерживаемых форматов:** клиент запрашивает доступные направления конвертации.

### 1.3 Контракт

#### 1.3.1 Конвертация файла

**Операция:** `POST /api/convert`

**Входные данные (multipart/form-data):**

- `file: binary` — исходный файл (CSV, JSON, XML или YAML).
- `targetFormat: string` — целевой формат: `csv` | `json` | `xml` | `yaml`.

**Проверки/валидация:**

- `file` обязателен, не пустой.
- Размер файла не превышает лимит, заданный в конфигурации для исходного формата.
- `targetFormat` обязателен и входит в допустимые значения.
- Исходный формат определяется по содержимому/расширению; должен быть поддерживаемым.
- Пара исходный → целевой должна быть допустимой (все 12 направлений считаются допустимыми).
- Структура исходного файла валидна для выбранного формата (синтаксически корректна).

**Логика/шаги (может быть изменена на собственное усмотрение):**

1. Принять файл и параметры.
2. Определить исходный формат.
3. Проверить размер файла по лимиту исходного формата.
4. Парсить исходный файл во внутреннее представление (объект/массив/таблица).
5. Преобразовать внутреннее представление в структуру, подходящую для целевого формата (для неоднозначных пар — по собственному усмотрению, см. п. 1.4).
6. Сериализовать в целевой формат.
7. Вернуть результат как потоковый файл.

**Ответы:**

- **200 OK:** файл в целевом формате, с заголовками `Content-Type` (соответствует формату) и `Content-Disposition: attachment; filename="converted.<ext>"`.
- **400 Bad Request:** невалидный файл, некорректные параметры, ошибка парсинга.
- **413 Payload Too Large:** превышен лимит размера для исходного формата.
- **415 Unsupported Media Type:** неподдерживаемый формат файла.
- **401 Unauthorized:** неаутентифицированный запрос.

#### 1.3.2 Список поддерживаемых форматов

**Операция:** `GET /api/convert/formats`

**Ответ:**

- **200 OK:** массив объектов `{ source: string, target: string[] }` — разрешённые направления (все 12 пар).

**Проверки:**

- Авторизация (JWT валиден).

### 1.4 Ошибки и ограничения

- Неподдерживаемый исходный формат.
- Некорректный синтаксис входного файла.
- Превышение лимита размера (лимит зависит от исходного формата, задаётся администратором).
- Неоднозначность преобразования (например, CSV → JSON: массив объектов vs массив массивов; XML → JSON: атрибуты, повторяющиеся элементы; JSON → XML: корневой элемент, массивы). Правила преобразования для неоднозначных пар определяются реализацией (фиксируются в коде/документации).
- Ошибки кодировки (не UTF-8, BOM).

### 1.5 Аудит/логи

- Логировать: `userId`, `sourceFormat`, `targetFormat`, `fileSize`, результат (`success` / `error` + код), длительность.
- Не логировать содержимое файла.

### 1.6 Нефункциональные требования

- **Безопасность:** валидация и санитизация входных данных; запрет внешних сущностей в XML; ограничение глубины/размера структуры; защита от ресурсных атак.
- **Производительность:** потоковая обработка для больших файлов; таймаут на конвертацию (например, 30 сек); кеширование результатов не требуется. Обработка файлов в отдельных потоках для избегания блокировки основного.
- **Надёжность:** корректная обработка Unicode, BOM, пустых файлов; атомарность ответа (не отдавать частичный файл при ошибке).
- **Совместимость:** поддержка актуальных версий форматов (JSON RFC 8259, YAML 1.2, XML 1.0, CSV RFC 4180).
