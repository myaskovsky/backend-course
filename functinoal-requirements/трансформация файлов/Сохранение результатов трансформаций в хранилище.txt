## 1) Сохранение результатов трансформаций в хранилище

### 1.1 Общее

**Назначение:** при выполнении трансформации файлов/изображений дать пользователю возможность сохранить результирующий файл в хранилище. Файл будет доступен для скачивания из истории трансформаций до истечения периода очистки истории.

**Пользователи/роли:**

- **Self:** сохраняет и скачивает только свои файлы.
- **Admin:** может скачивать файлы любого пользователя.

**Контекст/предпосылки:**

- Авторизация через access JWT (cookie).
- Трансформации файлов (`POST /api/convert`) и изображений (`POST /api/images/convert`) уже существуют.
- История трансформаций сохраняется для всех операций (см. ТЗ «Просмотр истории трансформаций»).
- Период очистки истории задаётся администратором (например, 90 дней).

**Зависимости/связанные настройки:**

- Хранилище файлов: локальное, S3-like, Firebase или другое (реализация скрыта за абстракцией).
- Таблица/коллекция истории трансформаций (связь с файлом).
- Фоновый процесс удаления истёкших записей и файлов.
- Конфигурация: срок хранения файлов (совпадает с периодом очистки истории).

### 1.2 Сценарии

1. **Сохранение результата:** пользователь выполняет трансформацию с флагом `save=true` → файл сохраняется в хранилище, создаётся запись в истории с идентификатором файла.
2. **Скачивание своего файла:** Self запрашивает скачивание сохранённого файла из своей истории → получает файл.
3. **Скачивание чужого файла администратором:** Admin запрашивает скачивание файла из истории конкретного пользователя → получает файл.
4. **Пропуск сохранения:** пользователь выполняет трансформацию без флага `save` (или `save=false`) → файл не сохраняется, запись в истории создаётся без ссылки на файл.
5. **Автоматическое удаление:** по истечении срока хранения запись и связанный файл удаляются автоматически.

### 1.3 Контракт

#### 1.3.1 Модификация запросов на трансформацию

**Операции:** `POST /api/convert` и `POST /api/images/convert`

**Дополнительный входной параметр (multipart/form-data):**

- `save: boolean` — флаг сохранения результата. По умолчанию `false`. Опциональный.

**Проверки/валидация:**

- `save` — если передан, должен быть корректным boolean (или строка `"true"/"false"`).
- Остальные проверки — по ТЗ соответствующей трансформации.

**Логика/шаги (дополнение к существующей логике):**

1. Выполнить стандартную трансформацию.
2. Если `save=true` и трансформация успешна:
    - сохранить результирующий файл в хранилище;
    - получить уникальный идентификатор файла;
    - создать запись в истории трансформаций с этим идентификатором и метаданными;
    - установить срок истечения хранения, равный периоду очистки истории.
3. Вернуть результат как обычно (потоковый файл). Сохранение не должно блокировать выдачу файла.
4. Если `save=false` — файл не сохраняется; запись в истории создаётся без идентификатора файла (если история ведётся для всех операций).

**Ответы:**

- Ответы на саму трансформацию не меняются (200, 400, 401, 413, 415 и т.д.). Сохранение является дополнительным действием на сервере.

#### 1.3.2 Скачивание сохранённого файла (Self)

**Операция:** `GET /api/transformations/history/{itemId}/download`

**Входные данные:**

- `itemId: string` — идентификатор записи истории трансформации.

**Проверки/валидация:**

- Авторизация (JWT валиден).
- Запись истории существует.
- Запись принадлежит текущему пользователю (`userId` из JWT совпадает с владельцем записи).
- Запись имеет сохранённый файл (поле `fileId` присутствует).
- Срок хранения файла не истёк.

**Логика/шаги:**

1. Авторизовать запрос.
2. Найти запись истории по `itemId`.
3. Проверить, что владелец записи — текущий пользователь.
4. Проверить наличие `fileId` и срок действия.
5. Получить файл из хранилища по `fileId`.
6. Вернуть файл потоково.

**Ответы:**

- **200 OK:** файл, заголовки `Content-Type` и `Content-Disposition: attachment; filename="<original-name>"`.
- **401 Unauthorized:** неаутентифицированный запрос.
- **403 Forbidden:** запись не принадлежит пользователю.
- **404 Not Found:** запись не найдена или файл отсутствует/истёк.
- **410 Gone:** файл удалён по истечении срока (опционально можно использовать 404).

#### 1.3.3 Скачивание сохранённого файла администратором

**Операция:** `GET /admin/users/{userId}/transformations/history/{itemId}/download`

**Входные данные:**

- `userId: string` — идентификатор пользователя-владельца.
- `itemId: string` — идентификатор записи истории.

**Проверки/валидация:**

- Авторизация (JWT валиден).
- Проверить право администратора (`transformations.history.admin`).
- Пользователь с `userId` существует.
- Запись истории существует и принадлежит указанному пользователю.
- Запись имеет сохранённый файл и срок хранения не истёк.

**Логика/шаги (может быть изменено на собственное усмотрение и в зависимости от используемого способа хранения файла):**

1. Авторизовать запрос.
2. Проверить право администратора.
3. Найти запись истории по `itemId` и `userId`.
4. Проверить наличие `fileId` и срок действия.
5. Получить файл из хранилища.
6. Вернуть файл потоково.

**Ответы:**

- **200 OK:** файл.
- **401 Unauthorized:** неаутентифицированный запрос.
- **403 Forbidden:** нет прав администратора.
- **404 Not Found:** пользователь или запись не найдена, либо файл отсутствует/истёк.
- **410 Gone:** файл удалён (опционально).

### 1.4 Ошибки и ограничения

- Файл не найден в хранилище (рассинхронизация записи и хранилища).
- Файл истёк и удалён.
- Попытка скачать чужой файл без прав администратора.
- Превышение лимита размера сохраняемых файлов.
- Ошибки хранилища (недоступность, сбой записи) — должны возвращать 500.

### 1.5 Аудит/логи

- Логировать: `userId`, `transformationId`, `fileId`, действие (`save`, `download`), результат (успех/ошибка), размер файла, длительность сохранения/скачивания.
- Не логировать содержимое файла.

### 1.6 Нефункциональные требования

- **Безопасность:** файлы приватны; доступ только по проверке прав (Self/Admin); прямая ссылка на файл не раскрывается; защита от IDOR; подписанные URL, если используется внешнее хранилище (опционально).
- **Производительность:** потоковая передача при скачивании; ограничение размера сохраняемых файлов; асинхронное сохранение (если возможно) для ускорения ответа.
- **Надёжность:** идемпотентность: повторный запрос скачивания должен возвращать тот же файл, пока он существует; обработка сбоев хранилища; автоматическое удаление по TTL должно быть надёжным (фоновый процесс).
- **Хранение:** срок жизни файла равен периоду очистки истории; файлы удаляются одновременно с записью истории; механизм удаления — фоновый (cron) или отложенное удаление (например, TTL в S3).
- **Совместимость (опционально, дополнительно):** абстракция хранилища позволяет подключать разные backends (локальный, S3, Firebase) без изменения бизнес-логики.
